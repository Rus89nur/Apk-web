Варианты реализации: справочник видов нарушений

Цель: один реестр (старые + новые виды), сопоставление для отчётов, в актах — как записано, в дашбордах/устранении/выгрузках — по новым видам. Меньше логики, чем сейчас — особенно на iOS.

Ваши требования (зафиксированы в макетах)

  • Справочник — все виды: активные, архивные, будущие добавления
  • Сопоставление — старый вид → новый вид (для аналитики)
  • В акте — хранится то, что выбрали (старый или новый)
  • В отчётах — всегда группировка по новым видам через карту соответствий
  • Лёгкость — без мастера, pending-seeds, migrateStoredVids при каждом открытии

Вариант 1 — Один экран «Справочник + сопоставление»

Один список с фильтром Все / Активные / Архив. У архивных строк — выпадающий «→ новый вид». Минимум навигации, хорошо на десктопе и телефоне.

+ Меньше экранов; всё видно в одном месте; проще код редактора
− Длинный список при 30+ видах; сопоставление менее наглядно, чем split-view

Вариант 2 — Два экрана: «Справочник» и «Сопоставления»

Справочник — только просмотр и добавление. Отдельная таблица «Старый → Новый» для настройки карты. Разделение «данные» и «миграция».

+ Понятно админу; таблица пар — наглядно; справочник не перегружен
− Два экрана; на iOS — ещё один push

Вариант 3 — iOS-first: bottom sheet + lazy load

На телефоне — карточка в настройках открывает bottom sheet: сначала только активные (20 записей max), архив и карта — по кнопке «Показать архив». Кэш resolve строится один раз при запуске.

+ Быстрый старт на iOS; мало DOM/View при открытии; архив не грузится до запроса
− Сопоставление в sheet тесновато; на десктопе лучше полноценный экран

Вариант 4 — Минимум UI: только таблица соответствий

Справочник пополняется автоматически из актов (orphan → archived). Пользователь только настраивает пары и добавляет новые active. Нет ручного «архивирования».

+ Максимально лёгкий UI; виды из старых актов сами попадают в архив
− Меньше контроля; «мусорные» строки в архиве если опечатка в акте

Рекомендация для вашего кейса

Вариант 1 (один экран) для веба + та же модель данных на iOS с lazy-архивом (идея из варианта 3). Сопоставление — inline у архивных строк, без мастера и без migrateStoredVids.
